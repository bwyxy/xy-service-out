# 踩坑实录：给博客写了个"一键分发"，被 CSDN 和掘金轮流上了一课

> 需求：在 [xiaee.cn](https://xiaee.cn) 写完一篇文章，**一键分发到掘金、CSDN、知乎、微信公众平台、简书、开源中国**，自动转格式、自动传图片、自动裁标题摘要，失败能重试，还要能拉回各平台的运营数据。
> 听起来是个"接几个接口就完事"的需求。实际上我踩了五个坑，最后一个只给了我四个字的报错。

## 0. 先定清楚架构：六个平台，六种脾气

做完调研就会发现，让六个平台接收同一篇文章，约等于让六个性格迥异的人吃同一道菜。

| 平台 | 正文格式 | 凭证 | 脾气 |
|------|---------|------|------|
| 掘金 | Markdown | Cookie | 挑剔，爱挑类型错 |
| CSDN | Markdown | Cookie + 动态签名 | 讲究排场，签名每次都要新 |
| 知乎 | HTML | Cookie | 富文本原教旨主义 |
| 微信公众平台 | HTML | AppId / AppSecret | 规矩最多，还要配白名单 |
| 简书 | Markdown | Cookie | 相对温顺 |
| 开源中国 | Markdown | Cookie | 相对温顺 |

方案是**适配器模式**：上层只管"把这篇发出去"，具体怎么发、发什么格式，由每个平台的适配器自己决定。加新平台只写一个类，业务代码一行不改。

围绕它做的配套：

- 凭证 **AES 加密落库**，接口返回时脱敏，编辑时留空表示不修改；
- 正文按平台做 **HTML → Markdown / 富文本** 转换，标题、摘要、标签按上限自动裁剪；
- 图片自动迁移到自有七牛图床并重写正文里的地址；
- 分发走**异步任务队列**（DB 任务表 + 线程池 + 定时扫描），不阻塞后台；
- 失败记录错误类型与原因，支持一键与批量重试；
- 定时拉取各平台浏览量、点赞、评论、收藏做聚合统计。

听起来很顺，下面是正片。

---

## 坑 1（架构级）：CSDN 的签名每次都得"新"，配置化模板直接出局

**最初的设想**：把接口地址、请求头、字段映射全存进数据库里的 JSON 配置，用一个模板驱动的适配器覆盖所有平台，最灵活。

**现象**：CSDN 的请求永远返回签名校验失败。

**根因**：CSDN 要求带 `x-ca-signature`，而签名串里包含一个 **nonce**——每次请求都得重新生成随机值，再拿 appSecret 做一次 HMAC-SHA256。

**固定的配置填不出动态的签名。** 这条路在 CSDN 这里就断了，只能为它写真实代码：

```
待签名串 = POST + "\n" + accept + "\n" + content-type + "\n"
         + "x-ca-key:203803574\n" + "x-ca-nonce:<每次随机>\n"
         + 请求路径

签名 = Base64(HMAC-SHA256(appSecret, 待签名串))
```

**教训**：待签名串必须**逐字符**对齐——多一个换行、少一个空格，服务端只会回你一句"签名错误"，不会告诉你错在哪。我在单测里对签名串做了逐字符断言，另外用一个独立实现的 HMAC 交叉验证签名结果。

## 坑 2（非官方接口的日常）：掘金的路由，说没就没

**现象**：

```
err_no: 2 —— 请求路由不存在
```

**根因**：**这个地址我们不用了。** 没有文档、没有弃用通知、没有 changelog。

**定位手法**：不带登录态去请求一批候选路径，用返回码当探针：

- 返回 `err_no 2` → 路由不存在；
- 返回 `403 must login` → **路由存在，只是没登录**。

扫一遍就出来了：路径从 `article/draft/create` 变成了 `article_draft/create`，下划线换了个位置。顺手还发现图床上传的路径一起失效了。

**教训**：排查问题不一定需要高深技巧，只需要一个能区分"存在"和"不存在"的信号。另外顺手搞清了掘金的发布是**两步**：先 `article_draft/create` 建草稿，再 `article/publish` 发布，两步都要做。

## 坑 3（类型）：Go 后端眼里，布尔值不是数字

**现象**：

```
json: cannot unmarshal bool into Go struct field ArticleDraftReq.is_original of type int16
```

**根因**：掘金后端是 Go 写的，`is_original`（是否原创）期待 **int16**，我传了 JSON 布尔值 `true`。改成 `1` / `0` 即可。

**这个报错其实是好消息**：它说明请求已经打到正确的接口、鉴权也过了，解码器只是在抱怨一个字段的类型。

**教训**：`cannot unmarshal` 是最好的报错，精确到字段名和类型。反过来说，**它的缺席也是一种信息**——如果所有字段类型都合法，你收到的就会是下一个坑里那句模糊的"参数错误"。

## 坑 4（最坑）：只有"参数错误"四个字，靠一次 SQL 破案

**现象**：

```
掘金创建草稿返回错误 2：参数错误
```

没了。不说哪个参数、为什么、应该是什么。

而我核对过：字段名全对、类型全对（否则坑 3 会再报一次）、分类和标签 ID 都是从官方接口取的真实值、摘要长度也落在掘金要求的 50~100 字内。

**定位**：既然接口不告诉我，我就**自己找相关性**。把分发结果和文章属性拉出来做交叉对比：

| 分组 | 有封面 | 无封面 |
|------|--------|--------|
| 分发成功 | 0 篇 | 11 篇 |
| 分发失败 | 4 篇 | 0 篇 |

相关性 100%。

**根因**：掘金要求封面图必须来自**它自己的图床**（`byteimg.com` 域名）。我在文章里填的是自己七牛图床的地址，外部地址过不了它的参数校验——于是它用最笼统的"参数错误"，把整篇文章拒了。

**解法**：只有封面地址已经属于掘金域名时才携带，否则留空，让平台自己从正文取图。

```java
String cover = context.getCoverImage();
if (cover != null && isJuejinHosted(cover)) {
    payload.set("cover_image", cover);
}
```

**教训**：当一个接口只给你模糊错误时，**别猜，去收集数据找相关性**。四个失败样本、十一个成功样本，一次查询就定位了。继续盲猜的期望收益是零。

## 坑 5（认知）：平台会累，机器不会；"分发成功"也不等于"已公开"

挖到这儿才发现是**两个问题**被我混成了一个。

**其一，限流。** 掘金通了之后，我把 25 篇文章一次性推给 CSDN，12 条失败，错误信息整齐划一：

```
CSDN 返回 HTTP 400：文章频繁发布，请稍后再试
```

这个锅不在代码，在我。**平台的限流是照着人的操作节奏设计的**——人在编辑器里写文章，一小时发一篇就不错了；而程序三分钟推了 25 篇，在风控眼里这就是标准的机器行为。解法是把每分钟请求数调到接近人的节奏，并分批推进；已成功的平台会被自动跳过，重试不会重复发布。

**其二，草稿不等于公开。** CSDN 第一次分发明明"成功"了，我点开回传的链接却打不开——因为发布规则里开了"只存草稿"。**任务成功只代表接口返回了成功码，不代表文章已经公开。** 草稿状态下的文章详情页必然 404，回传的链接应该给编辑器地址而不是详情页。

**教训**：一个模糊的"失败"背后可能藏着两个独立的问题，先分清再动手；以及，**状态语义要精确到字段**——`SUCCESS` 是接口层的成功，不是业务层的"已发布"。

## 复盘：这五个坑教了我什么

1. **非官方接口没有契约**，只有现象。路由会变、字段类型会变、错误码会含糊其辞。你要准备的不是文档，而是**探测与定位的手法**。
2. **模糊报错面前，数据比推理可靠**。接口不告诉你哪个参数错了，但失败样本和成功样本的属性对比会告诉你。
3. **类型错误是好消息，语义错误才是麻烦**。前者精确到字段，后者往往要靠自己缩小范围。
4. **适配器模式的价值在第六个平台才体现**。前五个平台各自写代码看不出差别，等你加第六个平台时，只需要新增一个类——这时候才值回票价。
5. **平台是给人用的，不是给脚本用的**。限流、风控、签名、白名单，这些机制的设计前提都是"人类操作节奏"。程序化接入时，把自己伪装成一个有耐心的人，比提高并发更容易成功。

## 结尾：分发不是目的，被看见才是

这套系统解决的是**体力问题**——复制、粘贴、调格式、传图片、改标题这些重复劳动，机器做比人快一万倍。

但它解决不了**内容问题**：如果一篇文章本身没人想看，发到六个平台也只是在六个地方没人看。

所以现在的流程是：在 [xiaee.cn](https://xiaee.cn) 认真写，写好一键分发出去，然后回到书桌前继续写下一篇。

**流量的事交给系统，写字的事交给自己。**
